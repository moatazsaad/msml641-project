# TerpLoad — Final Report

## 1. Problem and users

Before committing to a semester, UMD students have no reliable way to tell whether a
*combination* of planned courses will be too much. The pain rarely comes from one hard
class — it comes from several demanding courses landing in the same semester and
stacking badly (overlapping deadlines, back-to-back exam weeks, multiple project-heavy
classes at once).

TerpLoad is built for UMD CS/STEM students planning a required or workload-heavy course
combination — including students moving into harder major courses, students who don't
have a choice in which courses they take together, and students who simply don't know
how a schedule will feel until they're already in it.

We interviewed four students who had lived this problem: an Applied ML student who took
MSML604/605/606 together, a CS student combining project-heavy CS courses with
exam/essay-heavy GenEds, a CS+Econ student balancing CMSC216, CMSC250, organic
chemistry, and biology, and a CS student who took CMSC330, CMSC351, and STAT400
together. All four said the semester was harder than expected, and none of them could
have predicted that going in.

Before TerpLoad, students patch this together from friends who already took the
course, PlanetTerp, Reddit, past GroupMe chats, and academic advisors. Friends were the
most trusted source in our interviews, but that trust has a real gap: a friend may have
had a different professor, a different course structure, or simply not have struggled
the way the next student will. None of these sources combine multiple students'
experiences into one picture of a specific course *combination*.

## 2. Product

TerpLoad takes 3–5 planned UMD course codes and returns a Low / Medium / High workload
risk rating, the reasons behind it, and a per-course breakdown of which workload
signals (project-heavy, exam-heavy, homework-heavy, time-consuming) show up in real
student reviews — plus real review excerpts as evidence, so the student isn't just
trusting a number.

It ships as two interfaces sharing the same risk logic: a Streamlit web app (`app.py`)
and a command-line prototype (`src/simple_report_cli.py`). Both call the same
`estimate_schedule_risk()` function (`src/risk_rules.py`), so the risk *scoring* can
never disagree between them — only the underlying data source differs (the web app
runs live model inference; the CLI reads a pre-generated signal file).

**How it works end to end (the live web app path):**

```
Student enters course codes (e.g. CMSC330, CMSC351, STAT400)
        |
        v
Course profile already cached? -- yes --> skip ahead to risk scoring
        |
        no
        v
Fetch reviews from PlanetTerp's public API (src/planetterp_client.py)
        |
        v
Classify each review with the saved, fine-tuned DistilBERT model
(src/distilbert_inference.py)
        |
        v
Aggregate into a course workload profile: per-label positive rate,
True/False flag, low-evidence warning if under 10 reviews
        |
        v
estimate_schedule_risk() combines all courses' profiles into one
risk score, level, and list of reasons
(src/risk_rules.py — same function used by the CLI)
        |
        v
Report shown to the student: risk level, confidence,
best-move advice, per-course workload tags, evidence quotes
```

New courses are fetched and classified once, then cached — the app never retrains on a
student request. The CLI prototype (`src/simple_report_cli.py`) follows the same last
two steps but reads pre-computed signals from `data/course_workload_signals.json`,
generated by an earlier TF-IDF baseline (`src/predict_course_signals.py`) rather than
live DistilBERT inference. It was kept as the original testable prototype; the
Streamlit app is the current product.

## 3. NLP method and evaluation

**Task.** Multi-label classification on course review text: for each review, predict
whether it shows `project_heavy`, `exam_heavy`, `homework_heavy`, and/or
`time_consuming` signals.

**Data.** Reviews are collected from PlanetTerp's public API (`src/collect_planetterp_reviews.py`),
cleaned and deduplicated (`src/clean_reviews.py`), then weakly labeled by an LLM
following a written labeling prompt (`docs/labelling_prompt.md`,
`docs/labeling_guidelines.md`). A Week 11 audit hand-checked a sample and corrected 493
confirmed-wrong labels across the dataset (the audit focused on reviews wrongly marked
positive, not the reverse direction). The final labeled corpus has 5,059 reviews, split
70/15/15 into train (3,541), validation (758), and test (760) with a fixed random seed
(`src/split_labeled_reviews.py`) — the test set is only touched once, at final
evaluation.

**Baseline.** A keyword-matching baseline (`src/workload_baseline_signal.py`) flags a
label if the review contains any of a small set of keywords (e.g. "project", "exam",
"homework every week"). It has no learned weights and no context awareness.

**Models.** Two learned models were trained and compared under the same protocol —
5-fold cross-validation on the training split, threshold selection on validation only,
and a single held-out evaluation on the test split:

- **TF-IDF + Logistic Regression** (`src/train_tfidf_classifier.py`), class-balanced,
  one classifier per label.
- **DistilBERT**, fine-tuned per label as a multi-label classifier
  (`src/train_distilbert.py`), 3 epochs, batch size 8, max sequence length 256 tokens.

**Results (held-out test set, 760 reviews):**

| Model | Subset accuracy | Macro F1 | Micro F1 |
|---|---|---|---|
| TF-IDF | 0.537 | 0.652 | 0.667 |
| DistilBERT | 0.647 | 0.739 | 0.738 |

DistilBERT outperformed TF-IDF on every metric and was selected as the final model. It
is the model saved and loaded in production (`results/distilbert_model/`,
`src/distilbert_inference.py`).

Per-label DistilBERT test F1: `project_heavy` 0.746, `exam_heavy` 0.734,
`homework_heavy` 0.741, `time_consuming` 0.736.

**Where it fails.** Precision is lower than recall on every label for both models
(e.g. DistilBERT `project_heavy`: 0.67 precision vs. 0.85 recall) — both models lean
toward over-flagging a workload signal rather than missing it. Manual error review
(`docs/error_analysis.md`) found the models struggle most with "fair but heavy"
reviews (e.g. "projects were hard but fair" gets under-flagged as project-heavy) and
with implied workload that isn't stated in keywords (e.g. self-learning or heavy
outside study time). DistilBERT's 256-token input limit means long reviews are
truncated, so workload signals mentioned late in a long review can be missed. Courses
with fewer than 10 reviews get a low-evidence warning rather than a confident flag,
since small samples are unreliable. Finally, all of the numbers above are measured
against LLM-assigned weak labels, not a fully hand-labeled gold set — they show how
well each model matches the labeling process, not a validated ground truth.

## 4. User evidence

User testing directly shaped what got built, not just what got measured:

- Early interviews (4 students, described in Area 1) established that the real
  problem was course *combinations*, not single hard classes — this is why
  `risk_rules.py` scores multiple heavy courses together more harshly than any one
  course alone (e.g. a bonus penalty when 2+ courses are exam-heavy).
- After connecting real model-based signals to the CLI report, 10 additional students
  said the report was descriptive enough to influence their own decision-making.
- A round of 14 user testers evaluating the Streamlit report found: 14/14 (100%) said
  the report format was helpful, 14/14 (100%) found it easy to navigate, 9/14 (64%)
  wanted more professor-specific signals, and 3/14 (21%) asked what happens for
  courses with no reviews.
- That last finding directly led to two changes: the **low-evidence warning**, which
  did ship — any course under 10 reviews is explicitly flagged as a rough estimate
  rather than shown as settled fact (`course_profile_service.py`) — and a
  **grade-distribution fallback** (`src/grade_context.py`, `src/course_context.py`),
  which was built and unit-tested but is not yet wired into the running app. It
  remains a planned next step rather than a shipped feature.
- The confidence label and "best move" advice text shown in the app (`app.py`) were
  added directly in response to testers wanting more than a bare risk score — both are
  built from real review counts and risk results, not invented numbers.

## 5. Ethics and limitations

**Data rights.** All review text and grade data comes from PlanetTerp's public API
(`src/planetterp_client.py`, `src/collect_planetterp_reviews.py`), not scraped from the
site directly. Requests are rate-limited (2-second delay between calls) and cached
locally so the same course is never re-fetched. The reviews were already posted
publicly by students who chose to identify a course and professor.

**Privacy.** TerpLoad does not collect any data about the person using it. There is no
login, no account, and no record kept of which courses a student searched. The only
data stored is course-level review text and aggregate grade distributions, not
anything tied to an individual student using the tool.

**Bias.** The review data has a self-selection bias: it only reflects students who
chose to write a PlanetTerp review, which tends to skew toward strong opinions rather
than the average student experience. Courses with fewer reviews (new or small courses,
like most MSML courses) get less reliable estimates, which we handle with a
low-evidence warning. Labels are LLM-assigned ("weak labels"); the Week 11 correction
pass focused on fixing confirmed false positives (493 labels), since that was the
highest-impact direction to check within the project's timeline.

**What happens when the model is wrong.** Both models lean toward flagging a workload
signal rather than missing it — precision is lower than recall on every label for both
TF-IDF and DistilBERT. That's the safer failure direction for a workload warning tool:
a false alarm costs less than a silent miss. We also limit the damage either way —
reasons are phrased as "may have" rather than certainties (`risk_rules.py`),
low-evidence courses are explicitly flagged instead of shown as fact, and the tool
states outright that it does not replace academic advising or guarantee outcomes
(`docs/mvp_requirements.md`).
